# Post-hackathon — the entry's second life

Most teams push the repo and forget it. The repo is an asset; treat the week after as part of the event.

## Within 48 hours of submission

- [ ] Fix the README into a real one: demo GIF above the fold, what-it-does in one line, how to run.
- [ ] Add topics/tags for discoverability (`hackathon`, domain tags, `built-with-X` for sponsors).
- [ ] License file if the judges required it and you skipped it at hour 47.
- [ ] Pin the repo on your profile if it demos well — it's proof of speed under constraints.

## Judge + sponsor follow-up

- Reply to any judge feedback within days, while the event is warm — even a "thanks, here's what we cut" keeps you on their radar.
- If a sponsor's API was central, tag them when you post about it. Sponsor prizes often convert to credits, interviews, or intros.
- Write one public post-mortem post (what worked, what got cut, what the demo couldn't show). These travel further than the submission itself.

## If you won or placed

- Update the README badge and bio links immediately — the traffic spike lasts ~2 weeks.
- Extract the reusable part into a standalone repo/package; hackathon monorepos die, the single good tool inside them doesn't have to.

## If you're continuing it

- Decide within a week or accept it stays a demo. Half-continued projects are worse than honestly shelved ones.
- The first real step is never "add features" — it's making the demo path work for a stranger without you.
